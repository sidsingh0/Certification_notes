- Host Pool is a collection of Azure Virtual Machines that register to AVD as a session host. 
- These VMs have AVD Agent installed on them
- All the session hosts in the pool should have same image for consistent experience
- We control what applications (Excel, Word, Chrome etc.) users can see using app groups.
- 2 Types of Host Pools
	1. Personal
		- Each session host assigned to single user
		- Higher cost
		- Use case: heavy workloads like developers, editors etc
		- User Data can be stored inside the VMs storage itself
		- Updates are handled by windows endpoint
		- No scaling
		- Users can be assigned to dedicated session host or first available session host
	2. Pooled
		- Single session host can have multiple users. Max users are defined by Max Session Limit
		- Lower cost and higher flexibility
		- Usecase: Normal Office workers using apps like excel etc.
		- User Data is stored using FSLogix
		- Updates are handled by redeploying the instances using new master images
		- Auto-scaling (VMs are started based on load)
		- Load balanced based on user session count
		- Users are not assigned to dedicated hosts. After a user sings out and signs back in, their user session might get load balanced to a different session host

# App groups
1. Remote App
	1. When user clicks AVD, they only see the list of apps made available to them
	2. They do not see start menu, task bar, file explorer etc
	3. It is simple and only available with Pooled Host Pools
2. Desktop
	1. We provide entire desktop experience to the user with applications already installed on it

Workspaces are groups of Application Groups
It acts like a publishing layer for Application Groups
Users subscribe to workspace and see app groups inside of it
**We cannot directly publish App groups, They have to be associated to the Workspaces**

# User Sessions
1. Active 
	1. It is the state when the user is signed in and connected to the Session Host
2. Disconnected
	1. User has NOT signed out.
	2. User's session remains on the Session Host.
	3. Applications continue running.
	4. Memory (RAM) and session state are preserved.
	5. Common causes:
		- User closes Remote Desktop window.
		- Internet connection drops.
		- User disconnects intentionally.
3. Pending 
	1. It can take 30s - 5m to sign in.
	2. User authentication and session creation are in progress.
	3. The connection has started but the session is not yet fully established. Azure Virtual Desktop is preparing the session.
	4. Pending state reserves a spot in the session host, so if another user signs in before the current user, the current user is not kicked out
