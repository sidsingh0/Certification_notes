1. On-premise Identities
	1. Azure AD has to be involved, identities are discovered through Azure AD
	2. If user identities only exist in on-premise AD DS, are not supported
	3. Therefore we use hybrid identities
2. Hybrid Identities
	1. On-premise AD users are synced to the Azure AD using AD Connect
	2. Supports fedarated identities too
	3. Benefit: one account can access multiple services (SSO)
3. Cloud-only identities
	1. Users created and managed directly by Azure AD
4. Third Party identities
	1. IDP must be fedarated with Azure AD (Meaning Entra ID trusts the third-party provider.)
	2. User signs into Okta and Okta tells Azure AD user is okay
5. External Identities
	1. Means user from company A's entra ID can access AVD of company B
	2. This is not supported 
	3. Although we can use fedarated identities to make this happen

One issue:
We should not sign in to azure AVD with multiple user account simeltaneously.

# Authentication methods
1. Service Authentication
	1. User -> Entra ID -> Workspace is subscribed -> Desktop/App
2. MFA
	1. Used to increase security
	2. Use conditional access policies to implement
		-  Example: If user is outside company network -> Require MFA
3. Passwordless Authentication
	1. Windows Hello
	2. FIDO Keys
4. Smart Card Authentication
	1. ADFS is required

# Session Host authentication
After Azure has verified us, Session Host also has to verify us.
Windows Desktop Client(software we install to our blade PC to connect to the VM) supports:
- Username Password
- Smart Card
- Windows hello
- Azure AD

All the other clients only support Username and Password
MacOS also supports Smart Card

## Single Sign-On (SSO)
- User signs into company laptop:
```
John => Active Directory => Entra ID => AVD
```
- No extra login prompt.
- This is called **Seamless SSO**
- Exam keyword:  Hybrid Identity + Entra Connect = SSO


# Setting up connectivity between Azure AVD and on-premise devices
1. On-premise AD already exists: In this case we need Azure AD deployment on web, therefore to synchronize on-site AD to Azure AD, we use **Azure AD Connect**.
2. Non AD users on Premise: We can setup a **Fedarated Server** on-site. We create **Fedareted Service** in Azure and then allow it to trust the **On-site Fedarated Server**
3. Domain users on-premise who are willing to relocate AD DS to cloud:
	1. Azure AD DS: Service Provided by Azure, to which users can authenticate too 
	2. VM: Host AD services inside a VM
	3. Connect on-premise with Azure using ExpressConnect or VPN
