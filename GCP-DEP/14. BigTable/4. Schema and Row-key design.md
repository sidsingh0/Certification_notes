- BigTables are sparse
	- In BigTable, we do not need to have data in each column. Unlike other databases, BigTable allows no value instead of null. And these missing spaces don't cost any extra money.
- Column families group columns together.
- In Bigtable, you do not create or define individual columns ahead of time. You only set up **Column Families** (broad logical groupings of columns) when creating the table. (Columns do not need to be the same for each row, just like NoSQL)
	- The moment we create a datapoint with new column, that column is added to the column family
- Rowkeys are the unique identifiers for each row.
	- In BigTable, only RowKeys are indexed. So we need to design them carefully for our scenarios.

# Hotspotting
![[Pasted image 20260731084105.png]]
Because of Hotspotting, we are unable to utilize the distributed nature of the DB, therefore not being able to take advantage of it.
In general this happens when RowKey is set to something like this:
- sequential numbers
	- _All_ new writes hit the absolute end of the table (the latest timestamp). No matter how many times Bigtable splits the tablets, 100% of incoming write traffic constantly hits **only the single node** holding the latest time range. The rest of the cluster sits completely idle.
- timestamps

# Row Key Bad Practices
- Unreveresed domain names
- Sequential RowKeys
- Frequently updated keys
	- ex. User123_1950_{user-account-balance}

___
# Row Key Best Practices (Solve Hotspotting)

##### While storing domains, store them in reverse order
- Reverse domain names fix hotspotting by taking scattered prefixes (like `mail`, `maps`, `app1`) and turning them into **predictable, hierarchical prefixes** (like `com.google.mail`, `com.google.maps`).
- This creates continuous blocks of related data that **Bigtable’s load balancer can easily detect and split across multiple nodes**, while naturally spreading overall traffic across different domains (`com`, `org`, `net`) instead of piling all new writes onto a single node.
- Is all `com.google` data stored sequentially? Yes.    
- Will it overload a single node? Only temporarily. Bigtable will detect the high load on that key range and split `com.google.*` across multiple nodes.

#### For IOT data, timestamps at the end of the row key or reversed
![[Pasted image 20260731091506.png]]
Else, IOT data will be written in sequential order -> All writes will go to the same node

#### Use String identifiers
- Since these are not sequential, they are excellent choice for Row Key.
- ex. stock price identifiers (AAPL, AMZN etc.)

# Bigtable Key visualizer
- **Bigtable Key Visualizer** is a built-in diagnostic tool in Google Cloud Console that generates interactive **heatmaps** to show how read and write traffic is distributed across your row keys over time.
- Its primary purpose is to help you **identify performance bottlenecks, troubleshoot hotspotting, and validate your schema design**.
