### Lack of Acknowledgement[Read till the end, Important]
- In case subscriber is unable to issue Acknowledgement, Pub/Sub retries to send the message.
- However lets say some major problem has occured on the subscriber side,  
  Pub/Sub will keep trying to send the messages to the already overwhelmed subscriber
  This also increases message volume
- **This increase in message volume indicates an issue on the subscriber side.**
  **Our natural instinct is to check the Cloud Logging for that Subscriber**
- **If there are no errors being logged, it means our Subscriber's runtime error logging has been setup incorrectly. So we need to solve two issues:**
	- **Lack of error handling**
	- **Lack of acknowledgement**

### Solution to this problem:
Use exponential backoff: Increase time interval between each retry
Although there are many other backoff algorithms, in case of Pub/Sub exponential backoff is preferred
We cannot keep retrying till infinity, therefore:

### Max retries
- We setup max retries Pub/Sub does before finally marking the message as 
  **Permanently Failed**
- Now, we need to store these Failed messages for later investigation

### Dead lettering
- Same concept as DLQ
- In case of Pub/Sub **failed** messages are later sent to a separate topic: "**Dead Letter Topic**"
- Messages which have hit their max retries, are sent to this DLT

### Publish timeout
- This does not happen inside Pub/Sub
- However when building a good Pub/Sub system, one usually has something called Publish Timeout
- It refers to Publisher not being able to publish a message in a topic in a given time frame. Usually due to network errors etc.
- It is often highlighted by "Deadline Exceeded error"
- *This is very different from "acknowledgement deadline"*
- It is generated in publisher code only`
