### Tightly and Loosely coupled messaging systems
1. Tightly Coupled Messaging Systems
	1. Sender and Reciever is directly connected with no buffer
	2. If Reciever is down, system is more likely to fail (Messages might be missed)
	3. Basically system without queue in the middle
2. Loosely Coupled Messaging Systems
	1. Buffer in between
	2. Fault tolerant

# Pub/Sub 
- Global-scale messaging buffer
- It is a loosely coupled messaging 
- No-ops (Fully Managed)
- *It is similar to Apache Kafka, its scaling is handled by Google (no-ops)*
- Can connect to data pipelines like Dataflow.

# Common Exam Scenario
- On-prem kafka,ALMOST ALWAYS, migrates to Pub/Sub
	- Scalability
	- Global Reach
	- Reducing operational overhead
- *Cases where they might be used together:*
	1. HYBRID SYSTEMS: When both on-prem and cloud environments are required
	2. MIGRATIONS: Usually when migration is happening to cloud, both services can be active at once
	3. Collect Logs from on-prem Kafka and send them to GCP for analysis(Logs collected by kafka are published to Pub/Sub which sends this to bigquery, Dataflow for realtime analysis etc)
	4. App running in GCP with data on-premise

### For integrating Pub/Sub and Kafka
We have connectors:
1. Source connectors:
	1. Reads message from *Pub/Sub topic* and publishes them to Kafka
2. Sink connectors:
	1. Reads messages from one or more Kafka topic and publishes them to Pub/Sub topic
	2. Ex. Analyze data in cloud
Thing to note: Names are based from Pub/Sub POV
