Roles applied at organization level flow down to project/folder level.
Example: If i am assigned a role of organization administrator, i will get the same permissions while accessing the folder/project.

Main roles on organization level
1. Organization Administrator: Has access to everything. Can access and manage all the resources in the organization.
2. Organization Policy Administrator: Allows user to set strict access control and governance rules for all the resources, projects and folders.
   Ex. This role can create a rule, that disallows anyone in the organization to create cloud storage buckets
3. Viewer: Readonly access to everything in the organization
   Useful for audits and monitoring access
4. Browser: Readonly access to organizational structure (Organization, folders, projects), but cannot see the actual resources.
   Useful if someone wants to understand the structure of organization.

# Org policies
Used for compliance & governance
They allow us to enforce consistent rules throughout the organization
We do not have to manage each department separately
Ex. 
1. Require encryption, do not allow requests from some countries
2. Host all resources in tokyo -> compliance
IAM combined with these policies are great. Org Policies define how resources should be used and prevent outside attacks, and, IAM protects against internal accidents.

### Important policies to know:-
1. constraints/compute.resourceLocations: allow only to host resources in a said region
2. contraints/iam.allowedPolicyMemberDomains: People from which organizations are allowed to access the resource
3. constraints/compute.vmExternalIpAccess: Constrains or blocks VM from having an external IP. Therefore they are not exposed to the internet.
4. constraints/compute.requireOsLogin: No need to manage SSH keys, access is approved based on the IAM role.

Policies can be applied at organization, folder, project level.
For exceptions, we can override the policies at lower levels.
